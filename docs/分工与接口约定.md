# 多模态系统 · 分工与接口约定

> 三人协同开发。本文档是唯一的分工依据和接口依据，冻结后改动需三人同意。

## 1. 系统拓扑

```
                          前端 / 用户
                               │ HTTP
                               ▼
        ┌──────────────────────────────────────────────┐
        │  16GB 节点   llm_node      :8000              │
        │  FastAPI 网关（前端只访问这里）                │
        │    POST /api/chat    → Agent + vLLM(7B-AWQ) 8001
        │    POST /api/invoke  → 按工具名转发到视觉节点  │
        │    GET  /api/tools   → 聚合工具清单           │
        └───────┬──────────────────────────┬───────────┘
                │ /invoke                  │ /invoke
                ▼                          ▼
      ┌────────────────────┐    ┌────────────────────┐
      │ 8GB #1 vision-fast │    │ 8GB #2 vision-heavy│
      │ :8101  模型常驻     │    │ :8102  懒加载       │
      │ detect / classify  │    │ ocr / stylize      │
      └────────────────────┘    └────────────────────┘
```

## 2. 分工

| 成员 | 机器 | 目录 | 负责内容 | 交付 / 验收标准 |
|------|------|------|----------|----------------|
| **A** | 16GB | `llm_node/` | 统一网关、Agent 编排（LangChain）、vLLM 部署 Qwen2-VL-7B-AWQ | `/api/chat` 能对话；`/api/invoke` 能把工具请求正确转发到 B、C |
| **A** | 16GB | `kb_node/` | 项目知识库：文档切分入库（Chroma + embedding API），方案见 `docs/知识库方案.md` | `/invoke` 调 `kb_search` 返回带来源的检索结果 |
| **B** | 8GB #1 | `vision_fast/` | YOLOv8s、ResNet50，**模型常驻显存**（高频、要低延迟） | `/invoke` 调 `detect`/`classify` 返回真实结果 |
| **C** | 8GB #2 | `vision_heavy/` | PaddleOCR、风格迁移、文档读取，**懒加载 + 用完释放显存**（低频、模型偏重） | `/invoke` 调 `ocr`/`stylize`/`read_document` 返回真实结果 |
| **共用** | — | `common/` | 接口契约、工具注册表、节点外壳、配置 | 改这个目录**必须三人同意** |

原则：每个人只改自己目录；`common/` 是公共地带。这样三人可以完全并行，不用等对方。

## 4. 接口约定

### 4.1 通用约定

- 协议：HTTP + JSON（UTF-8）
- 附件：base64 字符串放在 `image` 字段，允许带 `data:<mime>;base64,` 前缀。
  **字段名是历史原因，实际承载任意附件**，网关按前缀里声明的 mime 分流：
  `image/*` 走视觉链路（附给模型 + 预取分析类工具）；
  `application/pdf`、`text/*`、代码文件走文档链路——网关调 `read_document`
  读成正文拼进用户消息，**不进多模态 parts**（把 PDF 当 `image_url` 发给 vLLM
  会直接 400）。**不带前缀一律按图片处理**（A 的测试台和老客户端都是裸 base64，
  这个语义不能改）。
- 端口：网关 `8000` / 视觉-快 `8101` / 视觉-重 `8102` / vLLM `8001` / 知识库 `8103`
- 超时：单次工具调用 `30s`，对话 `60s`
- 每个节点必须绑 `0.0.0.0` 才能被其他机器访问
- 节点 IP 用环境变量注入（`VISION_FAST_HOST` / `VISION_HEAVY_HOST` 等），**不要写死在代码里**
- 本地配置统一写仓库根目录 **`.env`**（模板见 `.env.example`，已 gitignore 绝不进库），
  详见 §8.1

### 4.2 视觉节点对外接口（两台 8GB 完全一致）

| 方法 | 路径 | 用途 |
|------|------|------|
| GET | `/health` | 存活 + 已注册工具名 |
| GET | `/tools` | 自报工具清单（网关照这个发现工具） |
| POST | `/invoke` | 统一调用入口 |

`GET /tools` 响应：

```json
{
  "node": "vision-fast",
  "tools": [
    {"name": "detect", "description": "目标检测，返回 bbox 列表",
     "needs_image": true, "params": {"conf": 0.25, "classes": null}}
  ]
}
```

`POST /invoke` 请求 / 响应：

```json
// 请求
{ "tool": "detect", "image": "<base64>", "params": {"conf": 0.25} }

// 成功
{ "ok": true, "tool": "detect", "result": {"boxes": []}, "error": null, "elapsed_ms": 42.1 }

// 工具内部报错（HTTP 仍是 200，不拖垮节点）
{ "ok": false, "tool": "detect", "result": null, "error": "RuntimeError: ..." }
```

### 4.3 网关对外接口（前端和 Agent 只认这些）

| 方法 | 路径 | 用途 |
|------|------|------|
| GET | `/api/health` | 聚合各节点健康状态，联调先看它 |
| GET | `/api/tools` | 聚合后的工具清单（Agent 靠它构建工具） |
| POST | `/api/tools/refresh` | 重新发现工具（节点加了工具后调） |
| POST | `/api/invoke` | 同 `/invoke`，但 `tool` 可来自任意节点 |
| POST | `/api/chat` | 对话主入口 |
| GET / DELETE | `/api/sessions`、`/api/sessions/{id}` | 历史会话列表 / 详情；DELETE 删除会话（不可恢复） |

`POST /api/chat` 请求 / 响应：

```json
// 请求
{ "session_id": "abc", "message": "图里有什么？", "image": "<base64 可选>" }
// image 也可以是 PDF / 文本文件：{ "image": "data:application/pdf;base64,JVBERi0..." }

// 响应
{ "reply": "……", "tool_calls": [{"tool": "detect", "ok": true, "result": {...}}] }
```

`stream: true` 时响应改为 SSE，事件为 `{type: delta|tool|done|error}`；**默认 false**，
不带这个字段仍是上面的 JSON。响应里的 `history_len` / `history_max` 供前端画
"记忆分界线"。

错误约定：未知工具 `404`，下游不可用 `502`，超时 `504`。

## 5. 工具契约 —— 加新工具怎么做

**每个工具只声明四件事**，别的都不用管：

| 字段 | 含义 |
|------|------|
| `name` | 工具名，**全局唯一**，网关发现重名直接报错 |
| `description` | 干什么用（会喂给 LLM 做工具说明） |
| `needs_image` | 是否需要输入图片 |
| `params` | 入参名 + 默认值（会转成给 LLM 的参数说明） |

节点自己维护工具清单，网关照和各节点启动时自动发现。所以：

**加一个新工具的完整流程（不改任何转发 / 编排代码）：**

1. 在所属节点实现该工具，声明上面四个字段；
2. 重启该节点；
3. 调一次 `POST /api/tools/refresh`（或重启网关）。

完事。之后 `GET /api/tools` 会出现它，Agent 自动多出一个能调用的工具。**网关和 Agent 的代码一行都不用动** —— 这就是我们说好的可扩展点。

工具放哪台的判断标准：**高频、要低延迟 → 8GB #1 常驻；低频、偏重 → 8GB #2 懒加载。**

## 6. 协作规则

1. **接口以本文档 + `common/schemas.py` 为唯一契约**。谁要加字段，先在群里说，三人同步后再改。
2. **先跑通 mock，再上模型**：三个节点先都能起、`/invoke` 返回空结果——这样三方立刻就能联调，不用等谁的模型先好。
3. **联调顺序**：各自本地起节点 → 网关 `/api/health` 全绿 → 打通 `/api/invoke` → 接真实模型 → 最后接 `/api/chat`。
4. 每个成员只改自己目录，`common/` 改动需三人同意。

## 7. Git 协作

**初始化**：一人 `git init` 推到 GitHub/GitLab（建私有仓库），另外两人 `git clone`。

**分支**：`main` 始终保持能跑；各自功能开 `feat/xxx` 分支，完成后再合并。

**`.gitignore` 必须包含**（权重和数据很大，绝不进仓库）：


**注意**：

- 提交前跑一遍自己节点的 `/health`，确保 `main` 上的东西是能起的。

## 8. 环境与启动

每台机器在仓库根目录装好依赖后，**按分工挑自己机器上要跑的节点**启动
（节点与人的对应见 §2；不在本机的节点用环境变量把 IP 指过去，见本节末尾）：

```bash
pip install -r requirements.txt

# 知识库 kb（:8103）：先入库（首次需 KB_EMBEDDING_API_KEY），再起节点
python -m kb_node.ingest
uvicorn kb_node.server:app --host 0.0.0.0 --port 8103

# 网关（:8000）：起前把远端节点 IP 注入环境变量
uvicorn llm_node.gateway:app --host 0.0.0.0 --port 8000

# 视觉-快（:8101）：权重在本机才起
uvicorn vision_fast.server:app --host 0.0.0.0 --port 8101

# 视觉-重（:8102）：权重在本机才起
uvicorn vision_heavy.server:app --host 0.0.0.0 --port 8102

# vLLM（:8001）：独立 venv，命令与参数见 llm_node/README.md
```

也可以用一键脚本起：`--mock` 全栈占位 / `--with-vllm` 连本机 vLLM /
`--only kb,gateway` 按节点自选（kb / gateway / vision-fast / vision-heavy / vllm
任意组合），详见根 README「快速开始」。

跨机联调时带上 IP：

```bash
VISION_FAST_HOST=192.168.1.101 VISION_HEAVY_HOST=192.168.1.102 \
  uvicorn llm_node.gateway:app --host 0.0.0.0 --port 8000
```

### 8.1 环境配置（.env）

配置三种写法，**优先级：显式环境变量 > `.env` > 代码默认值**：

1. **`.env`（推荐）**：复制根目录 `.env.example` 为 `.env` 按需填写，
   `common/config.py` 启动时自动加载，所有节点共用；改完重启节点生效。
   已 gitignore，key 绝不进库；
2. **`setx`（Windows 永久）**：`setx LLM_HOST "x.x.x.x"`——只对**新开**的窗口生效；
3. **临时**：PowerShell `$env:LLM_HOST="x.x.x.x"` / bash `LLM_HOST=x.x.x.x`，
   只当前窗口有效，临时覆盖某个值时用。

各节点配置清单（只在变量指的服务**不在本机**时才需要设 HOST 类变量）：

| 节点 | 变量 | 必配 | 说明 |
|---|---|---|---|
| kb (:8103) | `KB_EMBEDDING_API_KEY` | ✅ | 不配能起，但检索报错 |
| kb (:8103) | `KB_EMBEDDING_BASE_URL` / `KB_EMBEDDING_MODEL` | 可选 | 换 embedding 供应商才需要 |
| 网关 (:8000) | `LLM_HOST` | ✅ | vLLM 所在机器 IP（默认 127.0.0.1） |
| 网关 (:8000) | `VLLM_MODEL_NAME` | ✅ | **必须与 vLLM 的 `--served-model-name` 完全一致**（不一致：健康检查绿、一对话就报 502，去 `/v1/models` 里抄 id） |
| 网关 (:8000) | `VISION_FAST_HOST` / `VISION_HEAVY_HOST` | ✅ | 视觉节点不在本机时 |
| 网关 (:8000) | `KB_HOST` / `KB_PORT` | 可选 | kb 在本机时不用（默认 127.0.0.1:8103） |
| 网关 (:8000) | `CORS_ALLOW_ORIGINS` | 可选 | 前端来源固定时收紧跨域，默认 `*` |
| 任意 | `NODE_MOCK` | 可选 | `1` = 占位结果，不加载模型 |

网关侧与模型行为相关的（都有默认值，一般不用填）：

| 变量 | 默认 | 说明 |
|---|---|---|
| `VLLM_MAX_MODEL_LEN` | `4096` | vLLM 启动参数，也用来兜底算历史预算。**受显存限制**，填超了 vLLM 起不来，报错里会给出它估的上限 |
| `MAX_HISTORY_CHARS` | 自动 | 对话历史的**字符**预算，默认按**探测到的** vLLM 实际窗口减 3500 推导。超了从最旧的丢，最新的那条一定保留 |
| `MAX_HISTORY_MESSAGES` | `120` | 历史的**条数**上限，与上面的字符预算并行、谁先到算谁 |
| `LLM_TEMPERATURE` | `0.7` | **别设 0**：贪心解码下模型会退化成复读机 |
| `LLM_TOP_P` / `LLM_PRESENCE_PENALTY` | `0.8` / `0.8` | 同上，压制逐字复读 |
| `LLM_IMAGE_MAX_SIDE` | `1024` | 只影响**送给模型看的**那份图（缩长边）。工具拿到的始终是原图 |
| `TOOL_TIMEOUT` / `CHAT_TIMEOUT` | `30` / `60` | 秒。演示扫描件要调大（OCR 一页约 16 秒） |
| `DOC_MAX_SCANNED_PAGES` | `2` | 单个 PDF 最多 OCR 几页扫描页；**要和 `TOOL_TIMEOUT` 一起调** |

**自检**：起完 `GET /api/health` 一眼看全——哪项不 ok 看哪项的 `error`；
缺的多半就是上表打 ✅ 的没配。

## 9. 后续提升点

### 9.1 对话记忆：上下文压缩（候选，未排期）

现状：会话历史窗口 `MAX_HISTORY_MESSAGES = 12` 条（含工具消息），按工具调用
对对齐裁剪，测试台用 `history_len / history_max` 画"记忆分界线"提示遗忘。
百科知识已由 `kb_search` 外置（不占上下文），被裁的只有对话文本本身。

若需要更长的"有效记忆"，按性价比顺序做：

1. **扩窗口（零风险，先做）**：vLLM `VLLM_MAX_MODEL_LEN` 4096→8192 +
   `MAX_HISTORY_MESSAGES` 12→20，两处必须一起改。显存充裕（4B AWQ），
   唯一代价是长对话推理稍慢。
2. **机械话题压缩（折中）**：消息被裁时，把其中的**用户提问**机械拼接成
   一条「此前聊过的话题清单」留在上下文，AI 回答丢弃。零 LLM 调用、
   零幻觉，保话题脉络不保细节，适合 4B 模型。
3. **LLM 滚动摘要（最后考虑）**：被裁消息让模型摘要后拼回上下文。注意
   4B 模型摘要可能丢细节甚至编造，且摘要会永久留在后续每一轮——
   "记错"比"忘记"危害更大；真做需给摘要加约束并评估质量。

### 9.2 kb 检索目录过滤（候选，未排期）

现状：语料整体入库，`kb_search` 无法在查询时限定只搜某个目录——想
「问百科只搜 `wiki/`、问项目只搜 `docs/`」做不到，只能整体替换语料
（`python -m kb_node.ingest wiki`，见 kb_node/README）。

若要多语料共存 + 按需过滤，需要：

1. ingest 入库时给每块多存一个 `dir` 元数据（如 `wiki` / `docs`）；
2. `kb_search` 加可选参数 `source`，Chroma 查询带 `where` 过滤；
3. Agent 侧在工具参数说明里交代模型按问题性质选目录。

当前块级 metadata 已存 `file`（完整相对路径），扩展成本不高。
