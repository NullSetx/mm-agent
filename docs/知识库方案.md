# 多模态系统 · 知识库方案（kb_node）

> 本文是知识库的实现方案与选型依据。涉及 `common/` 的改动需三人同意（见 §7），
> 确认后按 §12 的顺序实施。

## 1. 目标与范围

让 `/api/chat` 能回答**项目自身文档**里的问题：「怎么启动」「谁负责什么」「接口
参数是什么」「有哪些已知问题」——素材就是 `docs/` 与 `README.md`，零额外整理。

**范围内**：`kb_search` 一个 LLM 工具；CLI 入库脚本；Chroma 向量库 + API embedding。
**范围外（后续扩展）**：用户上传文档、前端上传入口、多知识库、混合检索（BM25）。

## 2. 系统拓扑（新增 kb_node）

```
                          前端 / 用户
                               │ HTTP
                               ▼
        ┌──────────────────────────────────────────────┐
        │  16GB 节点   llm_node      :8000              │
        │  FastAPI 网关（前端只访问这里）                │
        │    POST /api/chat    → Agent + vLLM       8001
        │    POST /api/invoke  → 按工具名转发     ──┐   │
        │    GET  /api/tools   → 聚合工具清单       │   │
        └───────┬───────────────────────┬──────────┼───┘
                │ /invoke               │ /invoke  │ /invoke
                ▼                       ▼          ▼
      ┌──────────────────┐  ┌──────────────────┐  ┌─────────────────┐
      │ 8GB #1 vision-fast  │  │ 8GB #2 vision-heavy │  │ 16GB kb_node :8103 │
      │ :8101  模型常驻     │  │ :8102  懒加载       │  │ 纯CPU  kb_search   │
      │ detect / classify  │  │ ocr / stylize      │  │ Chroma+API向量  │
      └──────────────────┘  └──────────────────┘  └─────────────────┘
```

kb_node 与视觉节点同构：一个 uvicorn 进程、`GET /tools` 自报工具、`POST /invoke`
统一入口。跑在 16GB 机器（成员 A 的机器有空余，纯 CPU 不占显存）。

## 3. 选型与依据

### 3.1 部署形态：新节点，不做网关内嵌

| 方案 | 结论 | 理由 |
|------|------|------|
| **新节点 `kb_node/`** | ✅ 采用 | 完全复用 §5 可扩展点：网关/Agent 零逻辑改动自动发现；知识库可独立部署到任意机器；与「一个节点一个 uvicorn」的现有风格一致 |
| 网关内嵌 RAG 模块 | ✗ | 把内容服务混进编排层，网关从纯路由变成有状态服务；换机器、重启入库都牵连对话主链路 |

### 3.2 Embedding：API 为主 + 本地兜底（环境变量切换）

所有主流国内 embedding API 都兼容 OpenAI `/embeddings` 协议，kb_node 里一个
httpx 客户端（~30 行）通吃，**零新增依赖**：

| 候选 | 形态 | 价格 | 结论 |
|------|------|------|------|
| SiliconFlow `BAAI/bge-m3` | API | **免费**（1024 维，8K 上下文，中文检索强） | ✅ **默认** |
| 智谱 `embedding-3` | API | ~0.5 元/百万 tokens，注册送 2000 万 tokens | ✅ 备选（已有 bigmodel 账号，3 个环境变量切换） |
| 阿里 DashScope `text-embedding-v4` | API | 按量计费 | 落选：与上面同质，无优势 |
| OpenAI `text-embedding-3-small` | API | $0.02/M | 落选：需国际支付，中文无优势 |
| 本地 `bge-small-zh-v1.5` | sentence-transformers | 免费（~100MB，CPU 毫秒级） | ⭕ **兜底**：断网时 API 路线不可用，演示日网络不稳提前切 `KB_EMBEDDING_PROVIDER=local` |
| 本地 `bge-m3` | — | ~2GB | 落选：过重 |

**三条硬约束**（写入代码注释与 README）：

1. **入库与查询必须同一 provider + model**——向量空间不同检索必乱。切换
   provider 后必须重新入库；向量维度也随模型变（bge-m3 1024 / embedding-3 2048）。
2. **API key 只走 `.env` / 环境变量**，绝不进仓库（`.gitignore` 已覆盖 `.env`）。
3. **API 失败不炸对话**：embedding 调不通时 `kb_search` 返回 `ok=false`（HTTP 仍
   200，契约与视觉节点一致），LLM 如实告知「知识库暂时不可用」。

### 3.3 向量库：Chroma PersistentClient

| 候选 | 结论 | 理由 |
|------|------|------|
| **Chroma** | ✅ | `pip install chromadb` 即用；`PersistentClient(path=data/kb/)` 单目录持久化；自带元数据存储、增量增删；课程答辩「像样的向量库」 |
| FAISS | ✗ | 只是索引库：持久化、id→原文映射、元数据全要自己管，对这点数据是纯负担 |
| Milvus / ES | ✗ | 独立服务进程，违背轻量风格，运维成本不成比例 |
| 纯 numpy 暴力检索 | ⭕ | 这个量级（几十~几百块）性能完全够，但无元数据/增量管理，且答辩展示价值低——作为理解原理的备选记录在案 |

### 3.4 切分：自写中文切分器

不引 langchain-community（只为一个 splitter 不值得）。规则：

- 按 markdown 标题层级切块，块内超 500 字再按句子边界（。！？；\n）二次切分，
  相邻块重叠 ~50 字；
- 每块文本带「`文档名 › 章节路径`」前缀 + 元数据 `{"source": "docs/xx.md › §4.3"}`，
  前缀提高检索命中，source 让回答可标注出处。

## 4. 数据流

```
入库（离线，CLI）：                          查询（在线，LLM 驱动）：
python -m kb_node.ingest docs/ README.md    用户：'怎么刷新工具清单？'
  │                                           │
  ①读 md → 切分(§3.4)                         ①LLM 自主发起 kb_search(query=…)
  ②POST {base_url}/embeddings 批量向量化       ②kb_node：query 向量化（同一 API）
  ③Chroma upsert(id,向量,原文,source)          ③Chroma cosine topk
  ▼                                           ④返回 {hits:[{text,source,score}]}
data/kb/（Chroma 持久化目录，gitignore）      ⑤agent 渲染器润色成中文观察 → LLM 照着答
```

## 5. 工具契约（遵循《分工与接口约定》§5 四字段）

| 字段 | 值 |
|------|-----|
| `name` | `kb_search`（全局唯一，与视觉工具无冲突） |
| `description` | 动态生成（借鉴 stylize 的技巧）：固定句式 + 入库时统计的覆盖范围，如「检索多模态系统项目知识库（覆盖：分工约定、接口契约、启动步骤、已知问题）。用户询问项目本身的问题时调用」——帮 3B 模型判断何时该调 |
| `needs_image` | `False`（节点不收图、不解码，入参只有 params） |
| `params` | `{"query": "", "topk": 3}`——query 仿 stylize 惯例：默认 `""` + 运行时校验报错，模拟必填 |

`POST /invoke` 响应示例（JSON 可序列化，前端 tool_calls 面板直接可渲染）：

```json
{
  "ok": true, "tool": "kb_search", "error": null, "elapsed_ms": 182.3,
  "result": {
    "query": "怎么刷新工具清单",
    "hits": [
      {"text": "调一次 POST /api/tools/refresh（或重启网关）……",
       "source": "docs/分工与接口约定.md › §5", "score": 0.83}
    ],
    "total": 3
  }
}
```

入库不走 LLM 工具（不该让模型决定写库），走 CLI：`python -m kb_node.ingest docs/`。

### 7.1 Agent 侧渲染器（延续「小模型照着念」经验）

`render_for_llm("kb_search", result)` 输出带来源标注的中文观察，例如：

```
知识库检索到 3 条相关内容（可信来源，回答时注明出处）：
1. 【docs/分工与接口约定.md › §5】调一次 POST /api/tools/refresh……
2. ……
```

检索命中为空时明确渲染「知识库中没有相关内容」，让模型如实说不知道而不是编造。

## 9. mock 与测试约定

- `kb_search` 函数体开头 `mock_enabled()` 分支：返回结构合法的假 hits（与视觉节点
  惯例一致），三方不配 API key 也能全链路联调；
- `tests/test_kb.py` 沿用 conftest 的 toy-node 模式：embedding 客户端与 Chroma 全部
  fake（monkeypatch），**测试不出网**；覆盖：切分器边界、空 query 报错、命中/未命中
  渲染、embedding API 超时 → `ok=false`、网关发现 kb 工具的聚合。

## 10. 风险与降级

| 风险 | 处置 |
|------|------|
| embedding API 不可用 | `kb_search` 返回 `ok=false`，LLM 如实告知，对话不崩 |
| 演示日断网 | 提前 `KB_EMBEDDING_PROVIDER=local` + `sentence-transformers` 重入库（~2 分钟） |
| 换 embedding 模型 | 必须 reingest（向量空间/维度变了）；ingest 脚本检测 provider+model 变更时清空重建并打印警告 |
| 检索质量不足 | 先调 topk / 切分粒度；仍不行再上 BM25 混合或 rerank（列为后续，不在本期） |

## 11. 验收标准

1. `/api/chat` 问「怎么刷新工具清单」「ocr 在哪台机器」等项目问题，回答与 docs/
   原文一致且提到来源文档；
2. 问知识库没有的问题，模型如实说没有相关内容，不编造；
3. kb_node 宕机或 API key 错误时，`/api/chat` 正常返回、`tool_calls` 里 `ok=false`；
4. `NODE_MOCK=1` 且无 API key 时全链路可跑通；
5. 前端测试台零改动：kb_search 调用与结果自动出现在 tool_calls 面板。
